# Trade System — Validação Arquitetural V1

Domínio 01 · Integração e Dados de Mercado

Vamos iniciar pelo Market Data & Intelligence, que será a base de informação para os agentes de IA, o gerenciamento de risco, o treinamento dos modelos e a visualização das operações.

A proposta é validar três componentes:

1. Market Data Engine: aquisição, normalização, armazenamento e distribuição dos dados.
2. Feature Engine: transformação dos dados brutos em indicadores e características do mercado.
3. Market State Engine: consolidação do estado que será disponibilizado ao Trading Agent.

Minha recomendação é manter esses três componentes separados logicamente, mesmo que inicialmente sejam implementados em um único serviço.

## 2. Market Data Engine — O que vamos coletar?

Minha proposta inicial é organizar os dados em quatro grupos.

| Grupo                 | Dados                                                 | Prioridade      |
| --------------------- | ----------------------------------------------------- | --------------- |
| Market Data           | OHLCV, trades, volume, preços e order book            | P0              |
| Derivatives Data      | Funding Rate, Open Interest, Mark Price e Index Price | P0 para Futuros |
| Account Data          | Saldos, ordens, execuções, posições e margem          | P0              |
| External Intelligence | Blockchain, sentimento e macroeconomia                | P2              |

Os dados de conta serão adquiridos pelos adapters da corretora, mas a responsabilidade pelo estado financeiro consolidado continuará com o futuro Position & Portfolio Manager.

Para a primeira integração, usaremos BTCUSDT na Binance Spot e USDⓈ-M Futures. Os dois mercados terão identificação independente, pois seus preços, regras e eventos não são necessariamente iguais.

### Estratégia de aquisição

| Método           | Uso                                                          |
| ---------------- | ------------------------------------------------------------ |
| REST             | Histórico, recuperação de lacunas, snapshots e reconciliação |
| WebSocket        | Atualizações de candles, trades, book e eventos de conta     |
| PostgreSQL       | Persistência operacional e histórico inicial                 |
| Eventos internos | Distribuição das atualizações para outros componentes        |

O armazenamento precisará preservar timestamps de origem, timestamps de recebimento, mercado, símbolo, origem do dado e estado de qualidade.

## 3. Feature Engine — Como interpretar o mercado?

Aqui entra boa parte da inteligência quantitativa que fornecerá informações ao agente.

Proponho seis famílias de features.

  01 Price & Momentum
    OHLC, retornos, momentum, médias móveis, RSI e ATR

  02 Market Structure
    HH, HL, LH, LL, tendência, consolidação e rompimentos

  03 Smart Money Concepts
    BOS, CHoCH, Order Blocks, FVG e zonas de liquidez

  04 Volume & Order Flow
    Volume relativo, agressão estimada, desequilíbrio e profundidade

  05 Volatility & Regime
    Volatilidade realizada, regime de mercado e expansão/contração

  06 Derivatives Context
    Funding Rate, Open Interest, Mark Price e métricas de futuros

Decisão importante: as regras para identificar BOS, CHoCH, Order Blocks e FVG precisam ser formalizadas matematicamente e versionadas. Esses conceitos admitem diferentes interpretações; não podemos deixar sua identificação depender de uma avaliação visual subjetiva.

Também precisamos garantir que cada feature utilize somente informações que já estavam disponíveis no instante da decisão, evitando vazamento de dados futuros durante treinamento e backtesting.

## 4. Market State Engine — O que o agente recebe?

O Market State será uma representação estruturada do contexto de mercado em determinado instante.

Exemplo conceitual:
```
{
  "symbol": "BTCUSDT",
  "market": "USD_M_FUTURES",
  "timestamp": "2026-11-10T12:00:00Z",
  "timeframe": "5m",
  "price": {
    "close": 103250.0,
    "return": 0.0021
  },
  "structure": {
    "trend": "BULLISH",
    "last_bos": "BULLISH",
    "last_choch": null
  },
  "volatility": {
    "atr": 420.5,
    "regime": "MEDIUM"
  },
  "derivatives": {
    "funding_rate": 0.0001,
    "open_interest": 82500
  },
  "data_quality": {
    "valid": true,
    "complete": true
  }
}
```

Valores fictícios apenas para ilustrar o contrato de dados.

O Trading Agent também precisará receber `Position State`, `Portfolio State` e `Risk State`. Minha recomendação é que esses estados sejam mantidos em domínios próprios e combinados em uma Trading Observation no momento da inferência.

Isso evita misturar o estado do mercado com informações particulares de uma conta ou posição.

## 5. Timeframes — Proposta para validação

Sugiro manter o modelo multi-timeframe, com decisões inicialmente a cada fechamento de candle de 5 minutos.

| Timeframe | Responsabilidade                         |
| --------- | ---------------------------------------- |
| 1m        | Microestrutura e refinamento operacional |
| 5m        | Timeframe principal de decisão           |
| 15m       | Confirmação de estrutura                 |
| 1h        | Tendência e regime de mercado            |

O agente poderá receber informações dos quatro períodos, mas o fechamento do candle de 5 minutos será o gatilho inicial para avaliar uma nova decisão.

Isso não significa que o Risk Engine ou o Position Manager funcionarão apenas a cada cinco minutos. A proteção e o acompanhamento das posições precisam ocorrer continuamente.

## 6. Requisitos de qualidade e segurança dos dados

Antes de disponibilizar uma observação para a IA, o sistema deverá verificar:

- Integridade e sequência dos candles.
- Ausência de duplicidades e lacunas não tratadas.
- Sincronização dos timestamps.
- Atualidade dos dados em relação ao limite definido.
- Consistência entre símbolo, mercado e timeframe.
- Disponibilidade das features obrigatórias.
- Identificação de dados provisórios versus candles fechados.

Se um conjunto de dados crítico estiver inválido, o sistema não deverá gerar novas entradas com base nele. A proteção de posições existentes continuará por mecanismos independentes.

## 5. Próximo domínio — Inteligência Artificial

## Domínio 02 — AI & Learning Engine

Próxima etapa da validação arquitetural

Neste domínio validaremos a arquitetura e as responsabilidades dos três componentes principais:

Agente 01 — Research & Market Intelligence
  Pesquisa oportunidades, analisa ativos e regimes de mercado, produzindo contexto e recomendações. Sua implementação completa poderá ocorrer após o MVP do Agente 02.

Agente 02 — Trading Agent
  Responsável pela política de decisão operacional: abrir, manter, reduzir ou encerrar posições. Será o foco inicial do desenvolvimento de IA.

Learning Engine
  Ambiente de Reinforcement Learning, treinamento PPO/SAC, simulação, backtesting, avaliação, comparação e versionamento de modelos.

### Questões arquiteturais que validaremos

  1. Modelo de decisão: quais ações o agente poderá executar e quais parâmetros ele deverá definir.
  2. Trading Observation: como o agente receberá Market, Position, Portfolio e Risk State.
  3. Trading Environment: como simularemos o mercado, as execuções e as recompensas.
  4. Reward Function: como equilibrar retorno líquido, risco, custos e preservação de capital.
  5. Arquitetura de modelos: PPO, SAC e estratégias baseline, sem escolher antecipadamente um vencedor.
  6. Ciclo de aprendizado: como treinar, avaliar, aprovar e implantar novas versões sem comprometer o ambiente operacional.

Resultado esperado: aprovar a Arquitetura Conceitual do Domínio 02 e estabelecer os contratos entre os agentes, o Learning Engine e os demais componentes do Trade System.
