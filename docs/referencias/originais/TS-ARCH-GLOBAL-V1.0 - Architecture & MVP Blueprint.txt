# 3. Arquitetura C4 — Nível 1: System Context

O primeiro nível representa o Trade System como uma unidade de software e suas interações externas.

	Trader / Gestor / Operador
		Configuração · Supervisão · Aprovação · Intervenção
				↓ ^
	## TRADE SYSTEM V1
		Plataforma de Trading Automatizado com IA, Gestão de Risco e Supervisão Humana
		Market Intelligence - AI Trading - Risk & Execution - Operations
		↓ ^															↓ ^
	Binance 													Canais de alerta
		Market Data · Spot · Futures · 								Notificações · Incidentes · Eventos críticos
		Orders · Fills · Account

C4 Level 1 — Contexto lógico. Os canais de alerta representam uma integração a selecionar, não um fornecedor aprovado.

### Atores e sistemas externos

| Elemento          | Responsabilidade                                     |
| ----------------- | ---------------------------------------------------- |
| Trader / Operador | Acompanhar, intervir e executar comandos autorizados |
| Risk Manager      | Configurar e aprovar políticas de risco              |
| Administrator     | Administrar plataforma, usuários e ambientes         |
| Auditor           | Consultar evidências e rastreabilidade               |
| Binance           | Dados de mercado, execução e estados externos        |
| Canais de alerta  | Receber notificações operacionais                    |

A Binance será a única exchange integrada ao MVP. A arquitetura continuará preparada para adapters de outras corretoras, sem implementá-los antecipadamente.

# 4. Arquitetura C4 — Nível 2: Containers

No modelo C4, Container representa uma unidade executável ou um armazenamento de dados, não necessariamente um container Docker.

A proposta é consolidar os 33 componentes lógicos em um conjunto menor de unidades implantáveis.

## 4.1 Topologia lógica proposta

	Web Operations App
		Portal · Viewer · Console · Replay
			↓ ^
	Operations API / BFF
		Queries · Commands · Auth · Streaming
			↓ ^
	Trading Runtime — LIVE/PAPER  - Zona privada
		Market Data Service
		Feature & State Service
		AI Inference Service
		Risk & Control Service
		Execution Service
		Portfolio Service

	Data & Event Platform
		PostgreSQL
		Event Dispatcher
		Dataset & Artifact Storage
		Analytics / Read Models

	Training & Validation Platform
		Learning Engine · Backtesting · Walk-forward · Experiment Registry

	Platform Services
		IAM · Secrets · CI/CD · Observability · Backup · DR

	C4 Level 2 — Agrupamento lógico de implantação proposto. As setas representam dependências conceituais, não acesso irrestrito entre unidades.

## 4.2 Decisão de granularidade

Minha proposta é utilizar um monólito modular distribuído seletivamente como ponto de partida.

Isso significa preservar fronteiras de domínio, contratos e ownership de dados, mas evitar a criação prematura de dezenas de microsserviços.

Os componentes com requisitos diferentes de isolamento, escala ou falha poderão ser implantados separadamente.

| Unidade proposta               | Implantação inicial           |
| ------------------------------ | ----------------------------- |
| Web Operations App             | Separada                      |
| Operations API / BFF           | Separada                      |
| Market Data Service            | Separada                      |
| Feature & State Service        | Módulo ou serviço             |
| AI Inference Service           | Separada                      |
| Risk & Control Service         | Processo crítico isolado      |
| Execution Service              | Processo crítico isolado      |
| Portfolio Service              | Módulo ou serviço             |
| PostgreSQL                     | Serviço persistente privado   |
| Event Dispatcher               | Worker separado               |
| Dataset & Artifact Storage     | Armazenamento lógico dedicado |
| Analytics / Read Models        | Módulo ou worker              |
| Training & Validation Platform | Workloads isolados            |
| Platform Services              | Serviços transversais         |

Essa tabela apresenta 14 agrupamentos de implantação conceituais, e não 14 processos obrigatórios. Alguns representam armazenamentos ou capacidades de plataforma.

### Restrições importantes

- O Trading Agent só acessa diretamente a Binance para consulta.
- Somente o Execution Adapter autorizado utiliza credenciais de trading.
- Risk & Control permanece na rota obrigatória de autorização.
- Training não possui acesso às credenciais LIVE.
- Read Models não substituem estados autoritativos em decisões financeiras.
- Os processos críticos não dependem da disponibilidade da interface web.

A separação entre Risk, Execution e AI deve ser preservada mesmo quando dois módulos forem implantados no mesmo host.

# 5. Arquitetura C4 — Nível 3: Componentes

	No C4 Level 3, detalhamos os componentes internos das unidades executáveis mais importantes. Para esta etapa, proponho três recortes prioritários: Trading Runtime, Data & Event Platform e Operations Platform.

## 5.1 Trading Runtime

	Market Data Engine
		Ingestão · Normalização · Qualidade
				↓
	Feature Engine + Market State Engine
		Indicadores · SMC · Estado sincronizado
				↓
	Observation Builder + AI Inference
		Modelo aprovado · Action Mask · Trading Intent
				↓
	Control Manager → Risk Engine
		Modo operacional · Política · Sizing · Autorização
				↓
	Execution Engine + Binance Adapter
		Ordens · Idempotência · Reconciliation
				↓ ^
	Position & Portfolio Manager
		Posições · Equity · Margem · Exposição · PnL

O fluxo principal mostra a intenção de abertura. Proteções, cancelamentos e reduções seguras possuem caminhos operacionais próprios, sujeitos às políticas D03.

### Responsabilidade por decisão

| Decisão                                          | Proprietário                       |
| ------------------------------------------------ | ---------------------------------- |
| Qual informação de mercado está válida?          | D01 — Market State                 |
| Qual ação o agente propõe?                       | D02 — Trading Agent                |
| A ação é permitida pelo modo operacional?        | D03 — Control Manager              |
| A ação respeita o risco?                         | D03 — Risk Engine                  |
| Como a ordem será enviada e reconciliada?        | D03 — Execution Engine             |
| Qual posição e exposição efetivamente existem?   | D03 — Position & Portfolio Manager |
| Como persistir e rastrear o ocorrido?            | D05 — Data & Event Platform        |
| O sistema está operacionalmente pronto?          | D06 — OperationalReadiness         |
| Há evidências suficientes para liberar a versão? | D07 — Release Acceptance           |

Essa divisão impede que o modelo de IA acumule autoridade de análise, autorização financeira e execução.

## 5.2 Data & Event Platform

	Domain Services
		Estado + Evento de domínio
			↓
	PostgreSQL Transaction + Outbox
		Event Dispatcher
			↓
	Audit Trail - Read Models - Analytics

	Historical Market Data + Feature & Dataset Store
		Proveniência · Versionamento · Replay · Reprodutibilidade

A persistência transacional, a distribuição de eventos e a reconstrução analítica permanecem responsabilidades distintas.

O dispatcher pode ser inicialmente implementado sobre PostgreSQL Outbox, sem obrigatoriedade de Kafka ou RabbitMQ.

## 5.3 Operations Platform

A plataforma de operações deverá possuir duas fronteiras:

Consultas: visualização de mercado, posições, ordens, modelos, alertas, performance e replay, utilizando snapshots e projeções apropriadas.

Comandos: solicitações autenticadas, autorizadas e auditadas, encaminhadas aos componentes proprietários. A API de operações não poderá executar diretamente ordens na Binance nem modificar estados críticos sem passar pelos controles estabelecidos.

A interface deverá distinguir claramente:

- Intenção proposta pela IA.
- Decisão de risco.
- Ordem enviada.
- Execução confirmada pela Binance.
- Estado reconciliado da posição.

# 7. Fronteiras arquiteturais e dependências

A principal decisão desta etapa é definir quais responsabilidades devem permanecer isoladas e quais podem compartilhar infraestrutura.

| Fronteira             | Regra proposta                                     |
| --------------------- | -------------------------------------------------- |
| AI ↔ Risk             | IA propõe; Risk autoriza                           |
| Risk ↔ Execution      | Somente intenções autorizadas seguem para execução |
| Execution ↔ Binance   | Único gateway de ordens e reconciliação            |
| Execution ↔ Portfolio | Eventos de execução atualizam o estado operacional |
| D05 ↔ Domínios        | Persistência e eventos com ownership explícito     |
| Operations ↔ Runtime  | Consultas separadas de comandos                    |
| TRAINING ↔ LIVE       | Sem compartilhamento de credenciais LIVE           |
| CI/CD ↔ LIVE          | Promoção controlada por gates                      |
| Read Models ↔ Risk    | Projeções não substituem estados autoritativos     |
| Monitoring ↔ Control  | Alertas não contornam políticas de proteção        |

# 2. Etapa 02 — Mapa de Componentes e Dependências

TS-ARCH-GLOBAL-V1.0 / ETAPA-02 - Em validação

O objetivo desta etapa é transformar os 33 componentes lógicos aprovados em um mapa de engenharia com:

- Responsabilidade e proprietário funcional.
- Classificação arquitetural.
- Unidade de implantação proposta.
- Interfaces fornecidas e consumidas.
- Dados sob ownership.
- Dependências e criticidade.
- Participação no MVP.

É importante distinguir três conceitos:

| Conceito               | Significado                                            |
| ---------------------- | ------------------------------------------------------ |
| Componente lógico      | Responsabilidade definida na arquitetura               |
| Unidade de implantação | Processo, aplicação, worker ou armazenamento executado |
| Owner                  | Domínio ou equipe responsável por decisões e evolução  |

Um componente lógico não implica um microsserviço próprio. Da mesma forma, um serviço pode conter vários componentes, desde que preserve contratos, segurança e ownership.

## 3. Taxonomia arquitetural proposta

	RT Runtime operacional
		Processa dados, decisões ou comandos durante a operação.

	AI Inteligência e aprendizado
		Pesquisa, inferência, treinamento e validação de modelos.

	UI Interface e operações
		Experiência do operador, visualização e comandos.

	DATA Dados e eventos
		Persistência, distribuição, datasets e auditoria.

	PLAT Plataforma e infraestrutura
		Runtime, CI/CD, IAM, observabilidade e recuperação.

	ENG Engenharia e validação
		Qualidade, testes, simulação e homologação.

A taxonomia serve para organizar responsabilidades. Ela não substitui os sete domínios nem determina tecnologias.

### Regras de ownership

	1. Market State não é dono da posição financeira. Ele representa condições de mercado.
	2. Trading Agent não é dono da ordem. Ele produz uma decisão ou intenção.
	3. Risk Engine não é dono da execução. Ele autoriza, ajusta ou rejeita uma intenção.
	4. Execution Engine é dono do ciclo interno de ordens. A Binance é a autoridade externa sobre o que foi efetivamente aceito e executado.
	5. Position & Portfolio Manager é dono do estado operacional reconciliado de posições e portfólio.
	6. Control Manager é dono dos modos operacionais e bloqueios de controle.

O PostgreSQL armazena esses estados, mas a posse da infraestrutura de banco não transfere a autoridade de escrita entre domínios.

### Contrato crítico: Trading Intent → Risk → Execution

	TradingIntent
		AI ou operador autorizado
			↓
	ControlDecision
		Modo, autorização de controle e restrições
			↓
	RiskDecision
		APPROVED · ADJUSTED · REJECTED
			↓
	ExecutionRequest
		Somente intenção autorizada
			↓
	Order / Fill / Reconciliation
		Estado efetivamente reconhecido pela Binance

Invariante: nenhum componente pode converter diretamente uma `TradingIntent` em ordem na Binance sem a autorização aplicável de Control e Risk. Uma decisão `ADJUSTED` só poderá ser executada quando o ajuste estiver explicitamente autorizado pelo contrato.

### Separação entre ownership de negócio e ownership técnico

O D05 administra os mecanismos de persistência, mas não passa a decidir o conteúdo financeiro de uma posição ou a validade de uma política de risco.

Por exemplo:

- `execution.orders`: escrita controlada pelo Execution Engine.
- `portfolio.positions`: escrita controlada pelo Position & Portfolio Manager.
- `risk.decisions`: escrita controlada pelo Risk Engine.
- `control.state`: escrita controlada pelo Control Manager.
- `audit.events`: escrita controlada pelos mecanismos de auditoria, a partir dos eventos e comandos autorizados.

Os nomes físicos de tabelas e schemas ainda serão definidos. Esses exemplos expressam a responsabilidade lógica de escrita.

Nesta etapa, vamos especificar os dez fluxos críticos F01–F10 e estabelecer um padrão único de integração entre os componentes.

O resultado esperado é um conjunto de contratos técnicos suficientemente precisos para orientar a implementação, preservando as responsabilidades já aprovadas e sem antecipar escolhas físicas que ainda dependam do backlog de engenharia.

## 3. Modelo de integração proposto

A arquitetura utilizará três mecanismos complementares:

| Mecanismo | Uso                                         | Exemplo                  |
| --------- | ------------------------------------------- | ------------------------ |
| Command   | Solicitar uma ação com resultado controlado | `SubmitExecutionRequest` |
| Query     | Consultar um estado ou projeção             | `GetPortfolioSnapshot`   |
| Event     | Comunicar um fato já ocorrido               | `OrderFilled`            |

### Diretrizes

- Commands deverão possuir identificadores estáveis, autorização, validação e resultado rastreável.
- Queries deverão indicar versão e frescor do estado quando isso for relevante.
- Events deverão representar fatos, com versionamento e identidade própria.
- Comunicação síncrona será utilizada quando uma resposta imediata for necessária para a decisão.
- Eventos duráveis serão utilizados para propagação, auditoria, atualização de projeções e integração desacoplada.
- Não haverá pressuposição de transação distribuída entre PostgreSQL e Binance.

### Regra de autoridade

	Trading Intent
		Proposta de ação — IA ou humano
			↓
	Control Decision → Risk Decision
		Autorização obrigatória
			↓
	Execution Request
		Solicitação autorizada e idempotente
			↓
	Binance Order → Fill → Reconciliation
		Resultado financeiro confirmado

Invariante: um aceite de comando, uma autorização de risco ou um ACK de transporte não equivalem à confirmação de uma execução financeira.

## 4. Contratos transversais e schemas

Proponho utilizar um envelope padronizado para eventos e metadados equivalentes para comandos e consultas.

### 4.1 EventEnvelope v1

```
{
  "event_id": "evt_01...",
  "event_type": "execution.order.filled",
  "schema_version": "1.0.0",
  "correlation_id": "corr_01...",
  "causation_id": "evt_00...",
  "aggregate_type": "order",
  "aggregate_id": "ord_01...",
  "aggregate_version": 4,
  "environment_id": "PAPER",
  "account_id": "acct_01...",
  "market_type": "USDM_FUTURES",
  "symbol": "BTCUSDT",
  "event_time": "2026-11-10T18:00:00Z",
  "recorded_at": "2026-11-10T18:00:00.120Z",
  "producer": "execution-service",
  "payload": {
    "order_id": "ord_01...",
    "fill_id": "fill_01...",
    "executed_quantity": "0.001",
    "executed_price": "90000.00"
  }
}

```

Exemplo ilustrativo de contrato, não um evento real nem uma ordem executada.

| Campo               | Semântica                                   |
| ------------------- | ------------------------------------------- |
| `event_id`          | Identificador único para deduplicação       |
| `event_type`        | Nome canônico do fato                       |
| `schema_version`    | Versão do contrato                          |
| `correlation_id`    | Encadeamento de uma operação ponta a ponta  |
| `causation_id`      | Comando ou evento causador                  |
| `aggregate_id`      | Entidade cuja sequência deve ser preservada |
| `aggregate_version` | Versão monotônica no agregado               |
| `environment_id`    | TRAINING, PAPER ou LIVE                     |
| `account_id`        | Conta lógica associada                      |
| `event_time`        | Instante do fato na origem                  |
| `recorded_at`       | Instante de persistência interna            |
| `producer`          | Componente responsável                      |
| `payload`           | Dados tipados do evento                     |

Campos como `account_id`, `symbol` e `market_type` poderão ser opcionais para eventos de infraestrutura, mas deverão ser obrigatórios nos contratos financeiros em que forem aplicáveis.

Para dados de mercado, preservaremos também `received_at` e `available_at`, evitando vazamento temporal em backtesting e inferência.

Valores financeiros: preços, quantidades, taxas e valores monetários serão representados como decimais exatos nos contratos, sem dependência de ponto flutuante binário.

### 4.2 CommandEnvelope v1

```
{
  "command_id": "cmd_01...",
  "command_type": "execution.submit",
  "schema_version": "1.0.0",
  "idempotency_key": "execution:req_01...",
  "correlation_id": "corr_01...",
  "environment_id": "PAPER",
  "account_id": "acct_01...",
  "issued_at": "2026-11-10T18:00:00Z",
  "expires_at": "2026-11-10T18:00:05Z",
  "actor": {
    "type": "SERVICE",
    "id": "risk-engine"
  },
  "authorization_ref": "riskdec_01...",
  "payload": {
    "execution_request_id": "req_01..."
  }
}

```

A presença de `authorization_ref` não substitui a validação da autorização pelo componente receptor. Os comandos deverão possuir escopo, prazo de validade e proteção contra replay indevido.

### 4.3 Contrato de resposta

Proponho distinguir quatro estados de processamento:

| Estado      | Significado                                                  |
| ----------- | ------------------------------------------------------------ |
| `ACCEPTED`  | Comando recebido e aceito para processamento                 |
| `REJECTED`  | Comando recusado                                             |
| `PENDING`   | Processamento em andamento ou resultado externo desconhecido |
| `COMPLETED` | Resultado final do comando conhecido                         |

`COMPLETED` não significa necessariamente `FILLED`: uma ordem pode terminar cancelada, expirada ou rejeitada pela exchange. O ciclo de vida financeiro deverá ser representado separadamente.

| Falhas       | Reconexão, ressincronização, quarentena e invalidação de dados       |

## F02 — AI Decision & Trading Intent
Alta criticidade - Owner: D02

| Aspecto      | Contrato                                                                   |
| ------------ | -------------------------------------------------------------------------- |
| Entrada      | `ObservationSnapshot` com Market, Position, Portfolio e Risk State         |

Ações suportadas: `HOLD`, `OPEN_LONG`, `OPEN_SHORT`, `REDUCE` e `CLOSE`, respeitando as restrições de Spot e Futures.

O modelo deverá registrar não apenas a ação escolhida, mas também a versão utilizada, a observação de entrada e os metadados necessários à auditoria.

## F03 — Control & Risk Authorization
Crítico - Owner: D03 Control / Risk

| Aspecto      | Contrato                                                         |
| ------------ | ---------------------------------------------------------------- |
| Entrada      | `TradingIntent` ou `ManualIntent`                                |

| Comando      | `EvaluateTradingIntent`                                          |
| Identidade   | `intent_id`, `risk_decision_id`, `policy_version_id`             |
| Ordenação    | Avaliação contra versões autoritativas de estado e política      |
| Consistência | Limites financeiros verificados antes da execução                |
| Falhas       | Rejeição, expiração da autorização ou bloqueio de nova exposição |
| Aceite       | Nenhuma ordem sem autorização válida                             |

O Risk Engine deverá devolver `APPROVED`, `ADJUSTED` ou `REJECTED`, com justificativa e restrições aplicáveis.

Uma autorização de risco terá escopo e validade limitados. Se o estado de mercado, posição ou portfólio mudar materialmente antes da execução, será necessária revalidação conforme a política.

## F06 — Emergency Control & Circuit Breakers
Crítico - Owner: D03 Control / Risk

| Aspecto     | Contrato                                                            |
| ----------- | ------------------------------------------------------------------- |
| Entrada     | Alerta crítico, operador autorizado ou violação de política         |
| Comandos    | `BLOCK_NEW_EXPOSURE`, `CANCEL_OPENING_ORDERS`, `CONTROLLED_FLATTEN` |
| Saída       | `ControlStateEvent`, `EmergencyActionResult`                        |
| Autorização | RBAC, escopo, motivo e registro auditável                           |
| Ordenação   | Bloqueio efetivo antes de permitir novas entradas                   |
| Falhas      | Execução parcial, desconexão, estado de ordem desconhecido          |
| Aceite      | Nenhuma nova exposição não autorizada após bloqueio efetivo         |

`CONTROLLED_FLATTEN` não significa liquidação incondicional: a redução deve considerar ordens pendentes, posição reconciliada, regras da exchange e riscos de execução.

Os controles protetivos deverão permanecer operacionais durante `PAUSED`, quando tecnicamente possível.

# 6. Matriz de integração e garantias

A matriz abaixo resume os mecanismos recomendados para os dez fluxos.

| Fluxo | Mecanismo principal             | Garantia de ordenação               | Estratégia de falha               |
| ----- | ------------------------------- | ----------------------------------- | --------------------------------- |
| F01   | Streams + snapshots             | Por instrumento/stream              | Resync e staleness                |
| F02   | Snapshot + comando interno      | Por observação/decisão              | HOLD ou bloqueio de nova intenção |
| F03   | Comando síncrono controlado     | Por autorização e versão de estado  | Rejeição ou revalidação           |
| F04   | Comando + API Binance           | Por ordem                           | Idempotência e reconciliação      |
| F05   | Streams de conta + consultas    | Por ordem/posição, com deduplicação | Reprocessamento e reconciliação   |
| F06   | Comando prioritário de controle | Serialização por escopo de controle | Bloqueio e resposta segura        |
| F07   | Workflow + eventos              | Por versão de modelo                | Reprovação/rollback               |
| F08   | Comando autenticado             | Por comando e estado                | Rejeição, timeout e auditoria     |
| F09   | Outbox + dispatcher             | Por agregado                        | Retry, quarentena e replay        |
| F10   | Workflow de recuperação         | Sequência de checkpoints            | Permanecer bloqueado              |

### Consistência por categoria

	Estados financeiros críticos
		Exigem leitura autoritativa, versionamento e validação antes de autorizar novas exposições.

	Eventos e integrações
		Podem utilizar consistência eventual, com entrega durável, idempotência e recuperação.

	Analytics e interface
		Podem consumir projeções eventualmente consistentes, desde que indiquem frescor e estado de sincronização.

# 2. Etapa 04 — MVP Scope & Technical Prioritization
TS-ARCH-GLOBAL-V1.0 / ETAPA-04 - Em validação
===================================

O objetivo desta etapa é definir o menor sistema capaz de operar BTCUSDT de ponta a ponta em PAPER, com segurança, rastreabilidade e validação, além dos requisitos adicionais necessários antes de qualquer exposição de capital em LIVE.

A classificação proposta separa o que precisa ser implementado imediatamente, o que é bloqueante para LIVE e o que pode evoluir posteriormente.

## 3. Classes de priorização

## M0 MVP operacional em PAPER
	Implementar o fluxo Market Data → AI → Control → Risk → Execution Simulator → Portfolio → Audit, incluindo testes, dados históricos, backtesting e interface operacional mínima.

## M1 Bloqueantes adicionais para LIVE
	Credenciais reais, segurança reforçada, reconciliação com Binance, limites de capital, recuperação, observabilidade e homologação.

## M2 Evolução controlada
	Otimizações, análises avançadas, escalabilidade e funcionalidades que podem ser simplificadas inicialmente.

## M3 Pós-MVP
	Expansão multiativos, novas exchanges, pesquisa automatizada avançada e capacidades não necessárias ao primeiro ciclo operacional.

Regra de interpretação: M0 e M1 representam fases de entrega, não níveis de risco. Um item M1 pode ser altamente crítico e deverá ser antecipado para M0 se sua ausência comprometer a segurança ou a validade dos testes PAPER.

## 4. Recorte funcional do MVP BTCUSDT

### 4.1 Escopo incluído no M0

| Capacidade      | Entrega mínima                                                                  |
| --------------- | ------------------------------------------------------------------------------- |
| Market Data     | BTCUSDT Spot e Futures, candles 1m/5m/15m/1h, qualidade e sincronização         |
| Features        | OHLCV, retornos, momentum, volatilidade, estrutura de mercado e SMC versionados |
| Market State    | Snapshot sincronizado, com qualidade e frescor                                  |
| AI Trading      | Agente PPO candidato, ações permitidas e inferência a cada candle 5m fechado    |
| Learning        | Treinamento reproduzível, experimentos e registro de modelos                    |
| Backtesting     | Custos, slippage, funding, walk-forward e benchmarks                            |
| Risk Engine     | Políticas, sizing, exposição, limites e rejeição de operações                   |
| Control Manager | AUTO, SUPERVISED, MANUAL, PAUSED e emergency lock                               |
| Execution       | Paper Execution Adapter com ordens e fills simulados                            |
| Portfolio       | Posições, saldos, equity, exposição e PnL simulados                             |
| Data & Events   | PostgreSQL, Outbox, eventos, trilhas e replay mínimo                            |
| Operations      | Dashboard, gráfico, decisões, ordens, posições, comandos e alertas mínimos      |
| QA              | Testes de contratos, invariantes financeiros e falhas críticas                  |

### 4.2 Restrições funcionais

O M0 utilizará uma conta lógica PAPER inicial, BTCUSDT e os mercados Spot e USDⓈ-M Futures, com One-way Mode para Futuros.

Não serão necessários, no primeiro incremento, seleção automatizada de múltiplos ativos, gestão multi-exchange, estratégias avançadas de portfólio ou dashboards analíticos sofisticados.

O Research Agent permanecerá representado por seu contrato, sem exigir implementação completa.

### 4.3 Critério de conclusão do M0

O M0 estará funcionalmente completo quando for possível:

1. Receber dados de mercado e produzir Market State confiável.
2. Gerar observações e decisões com um modelo versionado.
3. Autorizar ou rejeitar intenções pelo Control e Risk Engine.
4. Simular ordens, fills e posições.
5. Reconstruir a cadeia completa de decisões e eventos.
6. Visualizar e intervir na operação em PAPER.
7. Executar backtesting, walk-forward e testes de falhas.
8. Comprovar os critérios G0–G2 aplicáveis, sem violações críticas.

Não é necessário demonstrar rentabilidade garantida para concluir a implementação técnica do M0. A aprovação da estratégia para promoção depende de critérios quantitativos específicos, definidos e testados separadamente.

### Observações sobre itens críticos

Há algumas pendências cuja fase primária precisa ser interpretada cuidadosamente:

- P08, P17 e P29–P32: se envolverem segurança essencial de PAPER, seus requisitos mínimos deverão ser antecipados ao M0.
- P59 — Integridade de auditoria: rastreabilidade básica é M0; reforços de integridade para LIVE são M1.
- P62 — Backup e recuperação: backups e recuperação mínimos também são necessários para proteger o ambiente PAPER; os critérios completos de LIVE ficam em M1.
- P65 — Provedor cloud: a escolha definitiva poderá ocorrer em M1, mas M0 exige um ambiente isolado e confiável, mesmo que local ou de desenvolvimento.
- P70 — Secrets Manager: a proteção básica de segredos é obrigatória desde M0; a integração segura com credenciais LIVE é M1.
- P82 — OperationalReadiness: uma versão mínima já será testada em PAPER, sendo reforçada para LIVE.
- P97 — Duração de PAPER: o período mínimo formal é condição de promoção; a capacidade de executar PAPER já pertence ao M0.
- P100 — Critérios quantitativos: sua definição começa no M0, mas a aprovação final dos limites de LIVE exige governança adicional.

A atribuição de P18 a M3 é provisória: deve ser confirmada contra a descrição original da pendência antes de encerrar o planejamento.

### Exemplo de história com critérios de aceite detalhados

TS-ST-011 — Paper Execution Adapter

M0

Objetivo: permitir que o Execution Engine processe ordens simuladas sem credenciais LIVE, preservando o contrato lógico de execução.

Cenários de aceite:

- Uma `ExecutionRequest` válida gera uma ordem PAPER com identidade estável.
- Repetir o mesmo comando com a mesma chave não cria uma segunda ordem.
- Uma ordem rejeitada pelo Risk Engine nunca chega ao adapter.
- Fills parciais atualizam corretamente a quantidade executada.
- Fills duplicados não alteram novamente posição ou PnL.
- Um timeout simulado produz estado desconhecido e reconciliação, não reenvio cego.
- Os eventos possuem `correlation_id`, versão e timestamps.
- O adapter não possui acesso a credenciais nem endpoints de execução LIVE.

Evidências: testes unitários, property-based, integração, contrato e execução E2E em PAPER.

## 7. Definition of Ready e Definition of Done

### Definition of Ready (DoR)

Uma história estará pronta para desenvolvimento quando possuir:

- Owner e componente responsável.
- Requisitos e ADRs vinculadas.
- Contratos de entrada e saída.
- Dependências identificadas.
- Cenários de sucesso, rejeição e falha.
- Critérios de aceite verificáveis.
- Ambiente e dados de teste definidos.

### Definition of Done (DoD)

Uma história estará concluída quando:

- A implementação estiver versionada e revisada.
- Testes automatizados aplicáveis estiverem aprovados.
- Invariantes financeiros relevantes forem demonstrados.
- Contratos e documentação estiverem atualizados.
- Logs, métricas e traces necessários estiverem disponíveis.
- Evidências estiverem vinculadas ao build.
- Não existirem defeitos críticos bloqueantes.
- O owner técnico aceitar a entrega.

Done não equivale a LIVE Ready. A homologação operacional exige os gates e aprovações definidos no D07.

## 4.2 Regras de promoção e suspensão

Uma promoção deverá ser bloqueada quando houver:

	- Violação de invariante financeiro crítico.
	- Modelo ou política não aprovados para o ambiente.
	- Reconciliação financeira crítica pendente.
	- Falha relevante de segregação de ambientes ou credenciais.
	- Evidências ausentes, inválidas ou incompatíveis com o build.
	- Critério obrigatório de gate não atingido.

Após a entrada em LIVE, incidentes críticos poderão exigir bloqueio de novas exposições, cancelamento de ordens de abertura ou redução controlada de risco, conforme a política operacional.

O retorno a PAPER e a revalidação serão obrigatórios nos casos definidos pelas ADRs de segurança e aceitação.
