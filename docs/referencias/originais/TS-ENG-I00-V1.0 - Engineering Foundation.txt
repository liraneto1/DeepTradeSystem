# TRADE SYSTEM V1 — Engineering Foundation

TS-ENG-I00-V1.0 · 11/11/2026

Proposta técnica em validação

Iniciamos a fase TS-ENG-I00-V1.0 — Engineering Foundation, utilizando como referência a baseline arquitetural aprovada `TS-ARCH-GLOBAL-V1.0`.

Nesta fase, a prioridade é transformar a arquitetura lógica em uma arquitetura física implementável, sem começar a programação antes da aprovação das decisões técnicas.

O monorepo modular está definido como estratégia de repositório. A stack tecnológica, os contratos físicos, as bibliotecas e a organização dos processos serão submetidos à aprovação.

## 1. Escopo e limites do I00

  Baseline arquitetural - Aprovada
  Monorepo modular - Definido
  Stack e arquitetura física - Propostas
  Implementação I00 - Não iniciada
  Execução LIVE - Desabilitada

O primeiro incremento deverá entregar uma fundação reproduzível com contratos, banco de dados, eventos, testes, observabilidade e controles de ambiente. Não inclui treinamento PPO, envio de ordens ou operação com capital real.

A arquitetura será preparada para Binance Spot e USDⓈ-M Futures, inicialmente BTCUSDT, sem acoplamento prematuro à corretora.

# 2. Arquitetura física proposta

Recomendo um monorepo Python, com monólito modular para o núcleo transacional e processos separados para funções assíncronas e de maior isolamento.

Essa abordagem preserva a decisão arquitetural já aprovada: não criar um microsserviço para cada um dos 33 componentes lógicos.

  ## Topologia de implantação — I00 e evolução

    Operations UI / API Clients
      Futuro portal e consumidores internos
          ↓
    API / BFF — FastAPI
      Autenticação, validação, consultas e comandos
          ↓
    Modular Trading Core
      Market Data / State
      AI Contracts
      Control / Risk
      Execution / Portfolio
  Fronteiras de domínio e ownership de escrita
                      ↓
    PostgreSQL              Event Dispatcher  
      Estado + Outbox         Worker separado 

  TRAINING, PAPER e LIVE serão segregados. No I00, somente os recursos necessários à fundação e aos testes estarão ativos.

### Processos físicos

| Processo             | Responsabilidade                                    | I00                            |
| -------------------- | --------------------------------------------------- | ------------------------------ |
| `api`                | Health, contratos, comandos e consultas de fundação | Esqueleto                      |
| `core`               | Módulos de domínio, casos de uso e políticas        | Esqueleto                      |
| `event-dispatcher`   | Publicar registros da Outbox                        | Implementar                    |
| `event-consumer`     | Deduplicação, checkpoints e handlers de teste       | Implementar                    |
| `postgres`           | Persistência operacional e Outbox                   | Implementar                    |
| `training-worker`    | Treinamento e avaliação PPO                         | Apenas fronteira               |
| `market-data-worker` | Binance REST/WS                                     | Apenas fronteira               |
| `operations-web`     | Portal e gráficos                                   | Posterior                      |
| `execution-adapter`  | PAPER e futura Binance                              | Interface, sem envio de ordens |

Regra obrigatória: nenhuma dependência de AI, UI ou Market Data poderá conceder autoridade de execução. Control e Risk permanecem obrigatórios antes de qualquer ordem.

## 3. Stack tecnológica proposta

| Camada           | Tecnologia proposta                                         | Justificativa                          |
| ---------------- | ----------------------------------------------------------- | -------------------------------------- |
| Linguagem        | Python 3.12+                                         | Ecossistema de IA, dados e integração  |

| Qualidade        | Ruff, mypy, pre-commit                               | Formatação, lint e tipos               |
| Runtime          | Docker Compose no desenvolvimento                    | Processos reproduzíveis                |
| CI/CD            | GitHub Actions                                       | Integração com o repositório GitHub    |

### Regras de dependência entre módulos

1. `shared` contém contratos e utilitários transversais, não regras de trading.
2. Domínios não acessam tabelas pertencentes a outros domínios diretamente.
3. Casos de uso dependem de interfaces; adapters implementam essas interfaces.
4. Dependências circulares entre domínios são proibidas.
5. A API não executa regras de Risk ou Execution por conta própria.
6. O treinamento PPO não possui dependência operacional do Execution Adapter.
7. Os serviços de execução não importam módulos da interface web.
8. O acesso a credenciais da Binance fica restrito ao adapter autorizado, quando implementado.

### Modelo de decisão técnica

  TS-ADR-093 — Transactional Outbox como mecanismo inicial de eventos
  Estado: PROPOSED · Domínios D05/D06 · Incremento I00

  Contexto: os fluxos F01–F10 exigem rastreabilidade e propagação confiável de eventos, sem presumir transações distribuídas.

  Decisão proposta: utilizar PostgreSQL para armazenar estado de negócio e registro de Outbox na mesma transação. Um dispatcher separado processará registros pendentes, com entrega at-least-once e consumidores idempotentes.

  Consequências: menor complexidade operacional inicial, mas necessidade de monitorar backlog, checkpoints, concorrência, ordenação por agregado e tratamento de falhas.

  Alternativas consideradas: Kafka, RabbitMQ e publicação direta após commit. Não são necessárias no I00 e poderão ser reavaliadas mediante requisitos mensurados.

  Critérios de aceite: demonstrar atomicidade, reprocessamento sem duplicidade financeira, recuperação após falha e ordenação por agregado.

A decisão de utilizar monorepo já foi definida pelo usuário; a TS-ADR-090 formalizará sua organização física e as regras de dependência.

# 6. Contratos iniciais do I00

Os contratos físicos deverão implementar os envelopes lógicos aprovados na Etapa 03. Os exemplos abaixo são propostas de schema, não alterações das decisões G20–G22.

## 6.1 CommandEnvelope v1

```
{
  "command_id": "cmd_01...",
  "command_type": "execution.submit",
  "schema_version": "1.0.0",
  "idempotency_key": "execution:req_01...",
  "correlation_id": "corr_01...",
  "environment_id": "PAPER",
  "account_id": "acct_01...",
  "issued_at": "2026-11-11T13:00:00Z",
  "expires_at": "2026-11-11T13:00:05Z",
  "actor": {
    "type": "SERVICE",
    "id": "risk-engine"
  },
  "authorization_ref": "riskdec_01...",
  "payload": {
    "execution_request_id": "req_01..."
  }
}

```

O comando deverá ser validado por tipo, versão, escopo, ator, expiração e chave de idempotência. A existência de `authorization_ref` não constitui, isoladamente, autorização válida: o Execution Engine deverá conferir sua integridade, vigência e correspondência com a solicitação.

## 6.2 EventEnvelope v1

```
{
  "event_id": "evt_01...",
  "event_type": "execution.order.filled",
  "schema_version": "1.0.0",
  "correlation_id": "corr_01...",
  "causation_id": "cmd_01...",
  "aggregate_type": "order",
  "aggregate_id": "ord_01...",
  "aggregate_version": 4,
  "environment_id": "PAPER",
  "account_id": "acct_01...",
  "market_type": "USDM_FUTURES",
  "symbol": "BTCUSDT",
  "event_time": "2026-11-11T13:00:00Z",
  "recorded_at": "2026-11-11T13:00:00.120Z",
  "producer": "execution-service",
  "payload": {
    "order_id": "ord_01...",
    "fill_id": "fill_01...",
    "executed_quantity": "0.001",
    "executed_price": "90000.00"
  }
}

```

### Invariantes dos contratos

| Área         | Regra                                                                   |
| ------------ | ----------------------------------------------------------------------- |
| Identidade   | `command_id` e `event_id` globalmente únicos                            |
| Idempotência | Mesmo comando lógico não pode duplicar efeito                           |
| Ordenação    | `aggregate_version` monotônica por agregado                             |
| Tempo        | UTC; `event_time`, `received_at` e `available_at` para dados de mercado |
| Finanças     | Decimal exato; sem `float` para valores monetários                      |
| Consistência | Persistência de estado e Outbox na mesma transação                      |
| Autorização  | Scope, ambiente, ator e decisão Risk válidos                            |
| Segurança    | TRAINING/PAPER/LIVE não compartilham credenciais operacionais           |
| Falhas       | Resultado desconhecido exige consulta e reconciliação                   |

### ADR de referência — TS-ADR-093

Transactional Outbox como mecanismo inicial de eventos
Domínios D05/D06 · Estado: PROPOSED

Contexto: os fluxos críticos exigem consistência entre persistência de estados e emissão de eventos.

Decisão: registrar mudanças de estado e mensagens Outbox na mesma transação PostgreSQL. Um dispatcher separado publicará os eventos para consumidores idempotentes.

Consequências: reduz a complexidade inicial, mas exige controle de retries, concorrência, ordenação por agregado, checkpoints e monitoramento.

Alternativas: Kafka, RabbitMQ ou publicação direta após commit. Permanecem opções futuras mediante necessidade comprovada.

Aceite: demonstrar atomicidade, recuperação após falhas e ausência de duplicação de efeitos financeiros.

### Requisitos operacionais

- Dispatcher com controle de concorrência, retries limitados, backoff e tratamento de mensagens não processáveis.
- Consumidores com deduplicação persistente e processamento transacional quando aplicável.
- Identidade de ambiente propagada nos contratos e nos registros.
- Health checks distintos para liveness e readiness.
- Logs estruturados com `correlation_id`, `causation_id`, `event_id` e `environment_id`.
- Métricas de atraso, tentativas, falhas e backlog de Outbox.
- Segurança fail-closed para configurações ausentes ou inválidas.

Apenas eventos sintéticos serão utilizados para validar o pipeline no I00. Não haverá ordens reais nem integração de execução com Binance.

## 4. Contratos iniciais
